# Backup encryption-key custody

Source: **HR-ENG-DEC-R1-003 D-08** (22 November 2026), "Adopt a dedicated, restricted backup-key
custody model". Enforced by `src/Support/KeyCustody.php` and reported by
`php bin/console backup:key-check`.

## What D-08 requires, and where each requirement is checked

| Requirement | How it is checked | State today |
|---|---|---|
| Dedicated key, not reused from application, database, hosting, SMTP or API secrets | by hand — a key generated for this purpose appears nowhere else | **owed**: no independent check, and `backup:key-check` cannot tell one base64 string from another |
| Stored outside the public document root | `KeyCustody::keyOutsideWebRoot()` — real paths compared | **ok** on the development instance |
| Restrictive permissions, `0600` where supported | `KeyCustody::keyFilePermissions()` | **ok on POSIX**; the check reports `warn` on Windows because modes are not ACLs there |
| Not beside the archives | `KeyCustody::keyNotBesideArchives()` — no key-shaped file in `var/backups` | **ok** |
| An independent recovery copy in a separate protected location | `KeyCustody::recoveryCopy()` against `BACKUP_RECOVERY_KEY_FILE` | **fail to provide**: no recovery copy exists |
| Key never in source control, logs, email, public storage or ordinary documentation | `.gitignore` for `.env`; `BackupAlert::sanitise()` redacts two shapes of key from failure records | **ok** for paths this repository controls |
| Custodians documented, recovery procedure documented | this file | **owed**: custodian names are blank |
| Restore tests performed and recorded using the recovery copy | the log below | **not performed** — there is no recovery copy to restore from |

The honest summary is in the last three rows: the key is held correctly on this host, and the
recovery half of the decision does not exist yet. A key on the same hosting account is, in D-08's own
words, "not equivalent to an independent vault or hardware security module".

## Recovery procedure (to be rehearsed, not assumed)

1. Obtain the recovery copy from the separate protected location. It must not be read over a channel
   that also carries an archive.
2. Place it where `BACKUP_RECOVERY_KEY_FILE` points, `0600`, owned by the account that runs the
   restore.
3. Restore the newest archive with `php bin/console db:restore <file> --yes` and confirm the row
   counts and a known record, not merely a zero exit code.
4. Record the date, the archive restored, the person and the outcome in the log below.
5. Remove the temporary copy if one was made, and leave the custodian's record unchanged.

**Do not rotate the backup key in a way that makes retained archives unrecoverable** (D-10). An
archive encrypted under an old key must remain restorable until it expires, which means the old key
is destroyed only after the last archive it opens has expired or has been re-encrypted and verified.

## Running the check

```
php bin/console backup:key-check
```

Exit code is `1` when any check fails and `0` when the only findings are warnings, so it can be put
in front of a release or behind a cron entry. A warning is not a pass: a missing recovery copy is a
warning because this host cannot create one, and the command says so on every run rather than letting
the gap be discovered during an incident.

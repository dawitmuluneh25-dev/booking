```
git fetch --tags

```

The second command is the point of the first: it reads the CI result **for that commit** rather than
assuming the latest run belongs to it.

## 2. What this candidate contains

Release 1 application code, complete:

- Foundation — front controller, explicit route manifest with declared access, CSRF, CSP, UTC storage,
  forward-only migrations (44 applied).
- Identity and RBAC — accounts, roles, permissions, two-act clinical authority separation (an account is
  administrative; referral authority is clinical and granted only by physician verification).
- Referral intake — guardian authority, quarantine, status links by token.
- Clinical review — dated, procedure-scoped approval; urgent pathway with claim and close as separate
  permissions.
- Procedure-day milestones — append-only events.
- Scheduling — one-winner slot guarantee under twenty concurrent processes.
- Notification outbox — retries with backoff, dead-letter after five attempts, recipient masking in logs.
- Retention — five calendar years (1,827 days), redaction that overwrites identity columns, document
  bytes deleted before the row is redacted, status links destroyed with the referral.
- Backup and restore — pure-PHP consistent dumps, 14 kept, restore drill that refuses a live target.
- Content versioning — dated, attributed publication.
- Referrer account request — public form, staff queue, approval that creates an account plus a
  **pending** physician profile, three anti-abuse layers, 60-day expiry.

## 4. Where the candidate can be tested today

**On staging, since 20 November 2026.** Staging runs release `20261120-225940`, built from this tag, with
artifact `sha256=6c245a2d0eef13af02fc427b60480a9ff430743820223d4d6c68959f139225ee` — the host computed the same
hash on arrival and recorded `result=ok`. It replaces `20261118-210723`, which was seven commits behind and
did not contain the HEAD fix, the public funnel change, the redirect-map contract, the control inventory or
the CI tooling. Staging remains behind HTTP basic auth and sends `X-Robots-Tag: noindex`, so it is not a
public copy of a clinical workflow.

The redirect map was rehearsed there and then removed: staging's own `.htaccess` was restored
byte-identically (`sha256=e32f62b5…`), so the seven legacy paths **404 on staging today**. That is expected.
The map is applied at cutover, not before — applying it now would make the application's own URLs
unreachable during UAT.

| Surface | Route | Notes |
|---|---|---|
| Landing page | `/` | Leads to the account request, not to a staff form |
| Service pages | `/services/{fnac, core_biopsy, abscess_drainage, intussusception}` | Published with dated attribution |

Staff surface — bookings, schedule, referrals, documents, admin queue, audit, diagnostics — is behind
sign-in and the named permissions listed in `README.md` §12.

## 5. Suggested UAT coverage

To be confirmed or replaced by the Clinical Lead; this is a starting point drawn from what the code
actually does, not a validated script.

**Reception, half a day**
1. Request an account from the public site; confirm the staff queue shows it with the submitted detail.
2. Approve it; confirm the account exists and the physician profile is **pending**, not active.
3. Submit a referral; confirm the confirmation page and the status link.
4. Attempt a document upload of a non-PDF, then a PDF; confirm the first is refused and the second lands
   in quarantine until released.
5. Book a slot; attempt to book the same slot twice; confirm the second is refused cleanly.

**Clinician, half a day**
6. Verify the pending physician; confirm referral authority changes only at that act.
7. Review a referral; record a dated, procedure-scoped approval; confirm the page states who approved and
   when.
8. Claim and close an urgent case; confirm the two permissions are separable.
9. Record procedure-day milestones; confirm they append rather than overwrite.
10. Sign out; confirm the session is gone and a protected route redirects to sign-in.

## 6. Known limitations at this tag

- ~~**Redirect map untested by a web server** (E4).~~ **Rehearsed on staging 20 November.** All seven legacy
  paths returned the intended 301, the three policy paths were never redirected, and every target was confirmed
  to resolve. It has still not been served from the production document root.
- ~~**HEAD on staging still 405**~~ — **fixed and deployed 20 November**; `curl -I /healthz` answers 200.
- **The policy pages are still 404** — `/privacy`, `/booking-policy`, `/referral-guidance` have no published
  version, so UAT cannot exercise them. That is a content-and-signature blocker, not a code one.
- **Suite duration is unstable on this workstation** (7:45 to 34:30 for the same counts). CI runs the
  same suite in about 80 seconds; the variance is local, not a property of the code.
- **`bin/console` is not covered by the style gate** — `phpcs` skips extensionless files. Recorded, not
  fixed.
- **Twelve ADRs sit at "Implemented, unapproved"**. They describe what was built; they are not clinical or
  product approvals.

## 7. If something is wrong with this candidate

Tag `v1.0.0-rc.2` from the fix. Do not move or re-point `rc.1` — a tag that can change is not a tag, and
UAT evidence recorded against it stops meaning anything.

To withdraw the candidate entirely:

```
git push --delete origin v1.0.0-rc.1
git tag -d v1.0.0-rc.1
```

That removes the pin and tells nobody; it should be accompanied by a note to whoever is scheduling UAT.
